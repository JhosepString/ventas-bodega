# D0 — Documento Base

**Proyecto:** Sistema de Ventas y Control de Stock para el Minimarket "La Esquina"
**Localidad:** San Vicente de Cañete
**Tipo de solución:** Aplicación web de uso interno
**Stack:** PHP 8 orientado a objetos, MySQL 8 (Laragon), PDO con sentencias preparadas, sin frameworks
**Versión:** 0.1 (documento base)

---

## 1. Problema

El Minimarket "La Esquina" comercializa abarrotes, lácteos, bebidas, conservas y productos de limpieza. Hoy no cuenta con un sistema que registre sus ventas ni controle su stock: anota las ventas en un cuaderno y controla la mercadería revisando físicamente los estantes. Como consecuencia, no sabe cuánto vendió al día y se queda sin productos sin enterarse hasta que un cliente los pide. Necesita una aplicación web interna que permita registrar productos con su stock, listarlos resaltando los que están en o por debajo del stock mínimo, registrar una venta (elegir producto y cantidad, tomar el precio vigente, calcular el total, registrar fecha y hora y descontar el stock) y listar las ventas del día con el total vendido del día.

---

## 2. Usuarios

El sistema tendrá un único usuario que concentra todas las operaciones (cajero/encargado del minimarket), de acuerdo con el supuesto de un solo cajero y dado que los roles están fuera de alcance.

### 2.1 Cajero / Encargado

**Qué hace:**

- Registra productos con código, nombre, categoría, precio de venta, stock actual y stock mínimo.
- Consulta el listado de productos y revisa cuáles están en o por debajo de su stock mínimo (resaltados).
- Registra una venta: elige el producto y la cantidad; el sistema toma el precio vigente, calcula el total, registra fecha y hora y descuenta el stock.
- Consulta las ventas del día y el total vendido del día.

**Cómo trabaja:**

Actualmente trabaja de forma manual con un cuaderno de ventas y la inspección visual de los estantes. Con la aplicación, realizará todo desde un equipo dentro del local: dará de alta y mantendrá los productos, consultará el stock mínimo resaltado para reponer a tiempo, registrará cada venta en el momento y revisará al cierre del día cuánto se vendió y por qué monto. Su trabajo se reduce a cargar datos en formularios y leer listados, sin necesidad de manejar consultas SQL ni cálculos manuales.

---

## 3. Proceso actual y dificultades

### 3.1 Proceso actual

1. **Registro de productos y stock:** No existe un registro formal de productos; el encargado conoce la mercadería por los estantes y la reposición se hace por memoria.
2. **Control de stock:** Se revisan los estantes físicamente para detectar faltantes; no hay un stock mínimo definido por producto.
3. **Registro de ventas:** Cada venta se anota a mano en un cuaderno, sin un cálculo confiable de totales ni un control de stock asociado.
4. **Cierre del día:** No existe un proceso de cierre; no se sabe cuánto se vendió al día ni qué productos están por agotarse.

### 3.2 Dificultades

- No se sabe cuánto se vendió al día, porque las ventas están dispersas en un cuaderno y no se totalizan.
- Se queda sin productos sin enterarse, porque el stock se controla solo mirando los estantes y no hay un stock mínimo que alerte con anticipación.
- El descuento de stock no se hace junto con la venta, lo que provoca diferencias entre lo anotado y lo que realmente hay en el estante.
- Los precios no están centralizados, por lo que el cajero puede cobrar precios inconsistentes.
- No existe un identificador único de producto, lo que dificulta localizarlo y actualizarlo.

## 4. Requisitos funcionales

Un requisito por cada punto del caso, sin agregar otros.

### RF-01 — Registrar productos

El sistema permitirá registrar un producto con los siguientes datos: **código (único)**, **nombre**, **categoría**, **precio de venta**, **stock actual** y **stock mínimo**.

### RF-02 — Listar productos con resaltado de stock mínimo

El sistema mostrará un listado de todos los productos registrados, **resaltando** aquellos cuyo stock actual está **en o por debajo** de su stock mínimo.

### RF-03 — Registrar una venta

El sistema permitirá registrar la venta de un producto. El cajero **elige el producto y la cantidad**; el sistema **toma el precio de venta vigente**, **calcula el total** (precio × cantidad), **registra la fecha y la hora** y **descuenta la cantidad vendida del stock** del producto. La venta y el descuento de stock ocurren juntos o no ocurre ninguno.

### RF-04 — Listar las ventas del día

El sistema mostrará las ventas registradas **del día** (con fecha y hora, producto, cantidad, precio y total de cada venta) y mostrará el **total vendido del día**.

## 5. Requisitos no funcionales

### Seguridad

- **RNF1 — Protección contra inyección SQL:** todo acceso a la base de datos usa PDO con sentencias preparadas; nunca se concatena SQL con datos ingresados por el usuario.
- **RNF2 — Protección contra XSS:** toda salida hacia las vistas se escapa con `htmlspecialchars`.
- **RNF3 — Protección contra CSRF:** cada formulario que modifica datos incluye un token CSRF que el servidor valida en cada petición POST.
- **RNF4 — Credenciales fuera del código:** las credenciales de la base de datos (DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASS) se leen desde `.env`, que está excluido del repositorio mediante `.gitignore`.
- **RNF5 — Manejo seguro de errores:** el usuario ve mensajes claros; nunca se muestran trazas ni detalles técnicos.

### Integridad de datos

- **RNF6 — Transacción de venta:** el registro de la venta y el descuento de stock se ejecutan en una sola transacción (beginTransaction / commit / rollBack); si algo falla, se revierte todo.
- **RNF7 — Restricciones en la base de datos:** `UNIQUE` en `codigo`; `CHECK (precio_venta >= 0)`; `CHECK (stock_actual >= 0)` y `CHECK (stock_minimo >= 0)`; `CHECK (cantidad > 0)`; clave foránea de `venta` hacia `producto`.
- **RNF8 — Precisión monetaria:** los importes se almacenan como `DECIMAL(10,2)`.

### Tecnología y entorno

- **RNF9 — Stack:** PHP 8 orientado a objetos con `declare(strict_types=1)`, MySQL 8 en Laragon (Apache en el puerto 81, MySQL en el 3307), PDO y sin frameworks.
- **RNF10 — Arquitectura en capas:** Model → Repository → Service → Controller → views; las reglas de negocio residen solo en los Services.
- **RNF11 — Uso interno:** la aplicación funciona en red local, sin despliegue público.

## 6. Reglas de negocio

Son las cinco reglas mencionadas en el caso:

1. **RN-01:** La **cantidad vendida debe ser mayor que cero** (`cantidad > 0`).
2. **RN-02:** **No se puede vender más de lo que hay en stock** (la cantidad vendida no puede superar el stock actual del producto).
3. **RN-03:** El **precio de venta no puede ser negativo** (`precio_venta >= 0`).
4. **RN-04:** El **código de producto debe ser único** (no se permiten dos productos con el mismo código).
5. **RN-05:** La **venta y el descuento de stock ocurren juntos o no ocurre ninguno**; ambas operaciones se modifican de forma complementaria dentro de una transacción.

## 8. Supuestos

1. **SUPUESTO 1:** Hay **un solo cajero** que opera el sistema.
2. **SUPUESTO 2:** **Una venta equivale a un solo producto** (no se venden varios productos en una misma venta).
3. **SUPUESTO 3:** La moneda utilizada es el **sol peruano (S/)**.
4. **SUPUESTO 4:** El entorno de desarrollo y ejecución es **Laragon** (en lugar de XAMPP).
